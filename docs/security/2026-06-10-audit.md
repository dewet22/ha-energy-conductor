# Security Audit — Energy Conductor

> Remediation tracked in [#7](https://github.com/dewet22/ha-energy-conductor/issues/7). This document is the dated audit artefact; the issue carries live status.

**Date:** 2026-06-10
**Scope:** Full working tree (integration code, frontend JS, CI/CD, dependencies, repo hygiene)
**Method:** Four parallel review passes (Python input validation & trust boundaries; hardware actuation path; frontend JS & serving path; supply chain & CI), with every reported finding manually verified against the source before inclusion. One agent-reported "Critical" was confirmed to be a false positive and is documented at the end.

---

## Threat model

Energy Conductor is a HACS custom integration that **commands physical battery inverter hardware** (charge targets, discharge limits) via `number.set_value` service calls. The relevant trust boundaries:

1. **Other HA entities** — sensor states/attributes read by the adapter (SoC, reserve, Solcast forecast, Octopus off-peak, EV charger). These are attacker-influenceable if any upstream integration is buggy or compromised, and are the primary input to hardware writes.
2. **Config entry data** — validated by the config flow at entry time, but readable/writable by anyone with filesystem or admin access.
3. **The entity registry** — entity IDs read back by the frontend strategy and embedded in generated dashboard config.
4. **The supply chain** — GitHub Actions, PyPI/npm dev dependencies, HACS distribution.

There is **no network code, no exec/eval/pickle/yaml.load, no registered services, and no persisted Store JSON** in the integration itself — the attack surface is narrow. Most findings below are defense-in-depth gaps on the path from untrusted sensor data to hardware writes, plus CI hardening.

## High

### H-1 — Unpinned GitHub Actions

**Files:** [hacs.yml:13](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.github/workflows/hacs.yml#L13), [test.yml:12-13,27](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.github/workflows/test.yml#L12)

```yaml
- uses: hacs/action@main          # floating branch ref
- uses: actions/checkout@v4       # mutable tag
- uses: astral-sh/setup-uv@v3     # mutable tag
- uses: codecov/codecov-action@v5 # mutable tag — receives CODECOV_TOKEN
```

`@main` executes whatever is at the branch tip at run time; tags can be force-pushed. A compromise of any of these repos (codecov's uploader was backdoored in 2021; `tj-actions/changed-files` in 2025) runs attacker code in this repo's CI with the default `GITHUB_TOKEN` (see H-2) and access to `CODECOV_TOKEN`.

**Remediation:** Pin every action to a full 40-char commit SHA with a version comment, e.g.:

```yaml
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
```

Resolve SHAs with `git ls-remote https://github.com/<org>/<repo> refs/tags/<tag>`. Consider enabling Dependabot for `github-actions` to keep pins fresh.

### H-2 — No `permissions:` block in workflows

**Files:** [test.yml](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.github/workflows/test.yml), [hacs.yml](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.github/workflows/hacs.yml)

Neither workflow declares `permissions`, so `GITHUB_TOKEN` gets the repo default — write access to contents, PRs, etc. unless the repo/org has opted into read-only defaults. Combined with H-1, a compromised action could push commits or tamper with releases.

**Remediation:** Add to both workflows (top level):

```yaml
permissions:
  contents: read
```

### H-3 — Non-finite floats pass `_read_float` and flow into plan math / hardware writes

**File:** [adapter.py:106-117](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L106)

```python
try:
    return float(state.state)
except (TypeError, ValueError) as exc:
    raise EntityProblem(...) from exc
```

`float("inf")`, `float("-inf")`, and `float("nan")` do not raise, so a sensor whose state string is `"nan"`/`"inf"` (upstream integration bug, recorder anomaly, or compromised integration) passes the guard. Downstream:

- **SoC / reserve %** → `overnight.plan_overnight` → `round(min(100.0, reserve + usable))` — `nan` makes `min()` return `nan` and `round(nan)` raises, killing the plan tick; `-inf` reserve produces a garbage target that is written to the charge-control entity (HA's number-entity min/max is the only remaining guard, and it's outside this integration's control).
- **Solcast `pv_estimate`** ([adapter.py:388](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L388)): one `inf`/`nan` slot poisons `total_kwh_forecast` for the night.
- **Recorder `change` rows** in the hot-water green-energy sum ([adapter.py:721-732](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L721)).

Note `baseline.py` and `learn_daily_target.py` already do this correctly with `_is_finite_number` — the pattern just needs to be applied at the other ingestion points.

**Remediation:** In `_read_float`, after conversion: `if not math.isfinite(v): raise EntityProblem(...)`. Add the same guard (skip-on-non-finite) to the Solcast slot loop and the recorder `change` sum. This single fix closes the widest untrusted-input → hardware path in the codebase.

## Medium

### M-1 — Registry entity ID embedded unvalidated in a Jinja2 template (markdown card)

**File:** [ec-strategy.js:181-184](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/www/ec-strategy.js#L181)

```js
content:
  "{% set r = state_attr('" + planId +
  "', 'reason') %}\n{{ r if r else '*No overnight plan computed yet.*' }}",
```

`planId` is the live `entity_id` read from the entity registry. The strategy intentionally follows renames, so a renamed entity ID is incorporated verbatim into a server-side-rendered Jinja2 template. An entity ID crafted to break out of the string literal (`') %}{{ ... }}{% set x = ('`) injects arbitrary Jinja2 into the markdown card, rendered with the *viewing user's* template context.

**Severity rationale:** renaming entities requires admin privileges in stock HA, so this is not a privilege escalation in most installs — but the template executes in every dashboard viewer's session, and HA's entity-ID slug rules are enforced by convention, not guaranteed by the WS API. Cheap to fix, so fix it.

**Remediation:** Validate before embedding; skip the card otherwise:

```js
var VALID_ENTITY_ID = /^[a-z_][a-z0-9_]*\.[a-z0-9_]+$/;
if (planId && VALID_ENTITY_ID.test(planId)) { ... }
```

### M-2 — Raw `config.device` reflected into a markdown card

**File:** [ec-strategy.js:246-250](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/www/ec-strategy.js#L246)

```js
return errorDashboard("The pinned device '" + state.want + "' was not found. ...");
```

`config.device` comes straight from dashboard YAML and is wrapped into markdown card `content` — the same render path as M-1 (markdown cards process Jinja2 templates). Whoever can edit the dashboard YAML can already do this with a plain markdown card, so this is not an escalation, but reflecting unsanitized input into a template-rendering sink is a pattern worth removing.

**Remediation:** Drop the value from the message ("The pinned device was not found — check the strategy's `device` option."). The YAML the user wrote is on screen anyway.

### M-3 — Missing plausibility clamps on values that drive hardware writes

**Files:** [adapter.py:257-270](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L257) (`_reserve_percent`), [adapter.py:143-151](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L143) (`_max_attr`), [model.py](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/model.py) (`Battery`), [overnight.py:64](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/overnight.py#L64)

Several physical quantities are used without range validation:

- **Reserve %** from the live sensor: a value of `0` (firmware reset, integration bug) lowers the overnight charge target floor to nothing; `>100` silently forces 100% targets every night. Not clamped to `[0, 100]` (or a sane floor like 1–4%).
- **`max` attribute** → `max_charge/discharge_power_w`: `int(raw)` accepts negative and absurdly large values; the discharge-guard writes `max_discharge_power_w` verbatim to the limit entity. No residential inverter exceeds ~20 kW.
- **`capacity_kwh`**: no `> 0` guard; `0` (storage edit / migration bug) → `ZeroDivisionError` in `plan_overnight` (caught by the coordinator's broad except, but the plan silently stops with an opaque error).

The existing `min(100.0, ...)` cap on the charge target and the binary (0/max) discharge regime absorb the worst outcomes — these clamps are defense-in-depth, not active vulnerabilities.

**Remediation:** Add a `__post_init__` to `Battery` asserting `capacity_kwh > 0` and `0 <= reserve_percent <= 100`; clamp `_max_attr` to `[1, 20_000]`; log a warning whenever a clamp fires.

### M-4 — Failed write commits the dedupe key, suppressing retry

**File:** [coordinator.py:246-249](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/coordinator.py#L246)

```python
except WriteFailure as exc:
    # Commit the dedupe key so the write (and its failure notification) does not
    self._dedupe[key] = decision.dedupe_key
```

Intentional (avoids notification spam), but it couples write retry to notification dedupe: a transient service failure at the off-peak→peak transition leaves the discharge limit at the *previous* value (e.g. 0 W) for the whole peak period, until the decision value next changes. For software whose job is actively managing hardware, a silently-stale actuator state is a safety/availability gap.

**Remediation:** Decouple the two — keep the failure-notification dedupe (`-failed` suffix already exists) but do **not** commit the write key on failure, so the write retries on the next tick.

### M-5 — Codecov: secret to an unpinned third-party action, upload failures masked

**File:** [test.yml:27-31](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.github/workflows/test.yml#L27)

`CODECOV_TOKEN` is handed to `codecov/codecov-action@v5` (mutable tag — see H-1) and `fail_ci_if_error: false` means upload failures (including token problems or endpoint compromise) pass CI silently. Token scope is limited to coverage upload, so impact is low, but pin the action (H-1) and either set `fail_ci_if_error: true` or document why not.

## Low

### L-1 — Time-string config parsing crashes on malformed stored values

**Files:** [adapter.py:289](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L289), [coordinator.py:137](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/coordinator.py#L137)

`hh, mm, *_ = (int(p) for p in raw.split(":"))` — a stored value without two colon-separated ints (manual storage edit, future migration bug) raises an unhandled `ValueError`. In `coordinator.async_start` this aborts listener registration during setup, silently disabling the integration. Wrap in try/except and fall back to the default time with a warning.

### L-2 — `float(decision.value)` outside the failure wrapper

**File:** [writer.py:31](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/writer.py#L31)

`Decision.value` is `Any`; a non-numeric value raises `ValueError`/`TypeError` *before* `_set_number`'s try/except, escaping the `WriteFailure` handling in the coordinator. Convert inside a try and re-raise as `WriteFailure`.

### L-3 — Silent entity redirect in `resolve_ref`

**File:** [entity_ref.py:85-95](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/entity_ref.py#L85)

When the unique-id lookup resolves to a different `entity_id` than the stored one (rename — the intended case — or a unique_id collision between two integration instances), nothing is logged. Write targets can move with no audit trail. Log at INFO when `found != entity_id`.

### L-4 — `coverage.xml` not gitignored

**File:** [.gitignore](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/.gitignore)

CI generates `coverage.xml` (`--cov-report=xml`); `.coverage` is ignored but the XML isn't. No secrets in it, just hygiene — add `coverage.xml`.

## Informational

### I-1 — PEP 758 syntax pins runtime to Python ≥ 3.14

**File:** [adapter.py:150](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L150), [adapter.py:390](https://github.com/dewet22/ha-energy-conductor/blob/0061b45717999ee3dde80e0b8e1c6d15e833b5e7/custom_components/energy_conductor/adapter.py#L390)

`except TypeError, ValueError:` (no parentheses) is valid PEP 758 syntax on Python 3.14+ and matches `requires-python = ">=3.14"`. But `manifest.json`/`hacs.json` gate only on HA `2026.1.0` — if any supported HA version for this floor runs Python 3.13, the module fails to import with a `SyntaxError` (integration completely dead on that install). Verify HA 2026.1's minimum Python is 3.14; if not, parenthesize the two `except` clauses. (Parenthesizing costs nothing and removes the foot-gun either way — two review passes both misread this as a Python 2 bug, which suggests human reviewers will too.)

### Untracked local files (no action needed, verified)

`.claude/settings.json` and `.claude/settings.local.json` exist in the working tree, are correctly gitignored, and are **not** tracked (`git ls-files .claude/` is empty). `settings.local.json` grants an MCP write tool to a live HA instance — keep it out of the repo; a global gitignore entry is a cheap belt-and-suspenders.

## What is done well

- **No runtime pip requirements** (`"requirements": []` in manifest.json) — eliminates the most common HACS supply-chain risk entirely.
- **No `eval`/`exec`/`pickle`/`yaml.load`/`subprocess`/template rendering** anywhere in the Python code; **no registered HA services**, so no externally callable surface.
- **No persisted Store JSON** — all learned state is recomputed from recorder statistics each tick; the "corrupted store drives bad writes" attack class doesn't exist here.
- **Write-mode gate** (`WRITE_MODE_LIVE`) checked unconditionally in `Writer.write()`, with dry-run as the default; no bypass path.
- **Charge target capped at 100%** in `plan_overnight`; **discharge guard is binary** (0 or max) — never an intermediate value derived from sensor data.
- **Write targets come from the config flow's `EntitySelector`** and are re-resolved via the entity registry by unique_id — never constructed from strings or sensor data.
- **Staleness gating** in `_read_float`; defensive `_read_bool`; `math.isfinite` filtering already present in `baseline.py`/`learn_daily_target.py`.
- **Frontend:** no DOM manipulation, no `eval`, no `postMessage` handlers, no prototype pollution; static path registration serves exactly one constant file (no traversal, no directory exposure).
- **Locked dependencies** with SHA-256 hashes (`uv.lock`, `package-lock.json`); `"private": true` in package.json; no committed secrets found anywhere in the tree; no `pull_request_target` usage.

## Remediation plan (suggested order)

1. **Now (cheap, highest leverage):**
   - H-3: add `math.isfinite` guard to `_read_float`, Solcast slot loop, recorder `change` sums.
   - H-1 + H-2 + M-5: pin all actions to SHAs, add `permissions: contents: read`, decide on `fail_ci_if_error`.
   - M-1 + M-2: entity-ID regex validation in ec-strategy.js; drop `state.want` from the error message. Bump `_STRATEGY_VERSION`.
2. **Next PR:**
   - M-3: `Battery.__post_init__` invariants + `_max_attr` clamp + warning logs.
   - M-4: decouple write retry from notification dedupe.
3. **Opportunistic:**
   - L-1 through L-4, I-1 (parenthesize the `except` clauses).

## Audit limitations

- Static review only — no dynamic testing, no fuzzing, and no review of git history for previously committed secrets.
- HA core behaviors (number-entity min/max enforcement, markdown card template sandboxing, WS API slug guarantees) were reasoned about, not tested against a live instance; M-1's exploitability depends on them.
- Dependency review covered lockfile integrity and known-bad patterns, not a CVE scan of each pinned version (`uv.lock`, `package-lock.json`). Running `pip-audit`/`npm audit` in CI would cover this continuously.
